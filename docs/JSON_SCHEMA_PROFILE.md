# JSON Schema Profile

`json_schema` implements a practical subset of JSON Schema 2020-12 for constrained generation. It does not claim complete JSON Schema conformance.

## Response Format

```js
const interpreter = runtime.createInterpreter({
  tokenizer,
  response_format: {
    type: "json_schema",
    json_schema: {
      type: "object",
      properties: {
        answer: { type: "string" },
      },
      required: ["answer"],
      additionalProperties: false,
    },
  },
});
```

`{ type: "json_object" }` is equivalent to constraining the root value to an object without additional property assertions.

## Supported Assertions

- Types and values: `type`, `const`, and `enum`. Supported types are `null`, `boolean`, `integer`, `number`, `string`, `array`, and `object`, including type arrays.
- Numbers: `minimum`, `maximum`, `exclusiveMinimum`, `exclusiveMaximum`, and `multipleOf`.
- Strings: `minLength`, `maxLength`, `pattern`, and recognized `format` values.
- Arrays: `minItems`, `maxItems`, `prefixItems`, `items`, `contains`, `minContains`, `maxContains`, and `uniqueItems`.
- Objects: `properties`, `patternProperties`, `propertyNames`, `required`, `additionalProperties`, `minProperties`, `maxProperties`, `dependentRequired`, and `dependentSchemas`.
- Composition: `allOf`, `anyOf`, `oneOf`, and `not`.
- Conditionals: `if`, `then`, and `else`.
- References: `$defs` and local `$ref` values containing JSON Pointer fragments, including escaped pointer segments.

Instance numbers are compared as exact decimal values rather than rounded JavaScript `Number` values. Consequently, integer classification, bounds, `multipleOf`, `const`, `enum`, and `uniqueItems` preserve distinctions beyond JavaScript's safe-integer range.

`pattern` and `patternProperties` use Unicode-aware JavaScript regular expressions.

## Formats

Recognized format assertions are:

- `date`
- `time`
- `date-time`
- `duration`
- `email`
- `hostname`
- `ipv4`
- `ipv6`
- `uuid`
- `uri`
- `uri-reference`
- `regex`
- `json-pointer`
- `relative-json-pointer`

Unknown format names are treated as annotations and are not asserted.

URI validation covers ASCII RFC 3986 syntax and generic authority structure. It does not provide full IRI or IDN handling. Email validation is a pragmatic ASCII subset rather than complete email-standard conformance. UUID validation is lexical and does not enforce version or variant bits.

## Annotations

The following annotation keywords are accepted without adding assertions:

- `$schema`
- `$id`
- `$comment`
- `title`
- `description`
- `default`
- `examples`
- `deprecated`
- `readOnly`
- `writeOnly`
- `contentEncoding`
- `contentMediaType`
- `contentSchema`

`$id` does not establish an external reference base.

## Generation Behavior

Prefix pruning can be conservative. A token may remain allowed when a later token will prove that the output cannot be completed. This avoids false negatives for assertions that cannot safely be decided from an incomplete document.

EOS handling is exact for supported assertions. EOS becomes eligible only when the generated bytes form a complete accepted document.

Object properties may be generated in any order. Duplicate properties are rejected during generation.

## Guidance Extension

A root schema can define `x-guidance`:

```json
{
  "type": "object",
  "x-guidance": {
    "item_separator": ",",
    "key_separator": ": ",
    "whitespace_flexible": true
  }
}
```

Only root-level `x-guidance` is supported. Separators are literal strings; regex-valued separators are unsupported.

## Unsupported Features

- `unevaluatedProperties` and `unevaluatedItems`
- `$dynamicRef`, `$dynamicAnchor`, and other dynamic-reference behavior
- External references
- Draft-07 compatibility forms such as tuple-form `items`, `definitions`, and legacy `dependencies`
- Complete IRI, IDN, and email-standard conformance

Unsupported assertion keywords fail during interpreter construction rather than being silently ignored.
